# 把上游宿主单测搬到鸿蒙上跑 —— 方案与现状

> 编制：2026-10-14 ｜ 状态：**架构已验证（26/27 链接通过），App 接线与真机运行待做**
> 相关：`PORTABLE.md`（分层）、`进度与待办-2026-10-14.md`

---

## 一、为什么做这件事

`dm/host/tests/` 里有 **27 个单测**，是**上游作者自己写的、真实的**代码。它们的价值在于：

1. **测的是"行为"，不是"能不能编译"** —— 正好补上"只验证到编译+链接、没验证跑起来"那个空白；
2. **是别人写的** —— 比自造样本更能暴露问题；
3. **覆盖的正是我们最没底的地方** —— 垫片的哈希算得对不对、时钟对不对、内存读得对不对。

**成本极低**：编译探针显示 **31/31 全部编过**（零额外工作，垫片层已经够用）。

---

## 二、搬法：读上游的构建定义，不另起一套

`dm/host/tests/Makefile` 里每个单测的源码清单都写在它那条 `clang` 命令里——**那是上游的权威**。
所以做的是**生成器**而不是手抄：

```
dm/ohos/tools/gen_host_tests.py
  → dm/ohos/host_tests_gen.c      （单测清单：外部声明 + 表）
  → dm/ohos/host_tests_gen.cmake  （源码清单 + 改名定义）
```

**上游改一个单测的依赖，重跑生成器即可，不会有"两边不一致"的问题。**

---

## 三、关键结论：必须"每个单测一个 .so"

这一条是**试出来的**，不是想出来的：

| 方案 | 结果 |
|---|---|
| **全部单测合成一个 .so** | ❌ **170 个未解析符号** |
| **每个单测单独一个 .so** | ✅ **26/27 链接通过** |

**为什么合成不了**（值得记下来）：上游在 macOS 上靠 `-dead_strip`——
把"这个测试没调到的函数"连同它们的未解析引用一起丢掉。
所以在苹果上"只链一部分宿主"没问题。而 ELF 上 `-shared` 会**导出全部符号**，
`--gc-sections` 也因默认可见性而丢不掉 → 引用的那些宿主函数全都变成未解析。

**所以必须照上游的结构：每个单测一个 .so**（对应上游"每个单测一个可执行文件"）。
这也再次印证 `PORTABLE.md` 里那条判据：**能读原项目的构建定义，就不要另起一套。**

### 逐个链接的实测结果

```
✅ 26 个通过：t_altstack t_audio t_audio_spsc t_cloudsync t_condvar t_doorspot t_fs
   t_fs_case t_hid_receipt t_hid_script t_hud_dead t_i18n t_modetx t_movie t_namegen
   t_oe t_padmap t_romfs_validate t_swkbd t_target_rank t_textbox t_thread_leak
   t_touch t_touch_mac t_unit_level t_widget
❌  1 个未过：t_rift_clock（16 个未解析）—— 上游这条规则用了 -dead_strip，
      我们在鸿蒙侧要补上等价的"隐藏可见性 + gc-sections"，或把缺的宿主文件补进它的清单
```

**另外要注意**：单测在鸿蒙侧会引用我们自己的两个文件，必须一起链：
`dm/ohos/dm_log.c`（日志）与 `dm/ohos/audio_ohos.c`（音频后端）。
另外要链 `-lhilog_ndk.z -lm -lz`。

### 单测的"通过/失败"怎么表示

**好消息**：这批单测**不用 `assert`**（只有 7 个文件用了 `assert/abort/exit`），
它们自己数失败数、用**返回值**表示结果（`0` 通过 / 非 0 失败），诊断信息走 `printf`。
所以跑测框架不需要复杂的信号处理。

## 四、跑测框架（已写好，未接线）

`dm/ohos/host_tests.c` + `.h`：

- 表由生成器产出，框架**不认识具体哪些单测**；
- **每个单测跑完立刻把结果写进日志文件**并打一份 hilog —— 这样即使后面某个单测把进程搞崩，前面的结果也已经在盘上；
- 单测自己的 `printf` 被**引到临时文件**（不然在 App 里根本看不到），失败时把前几行带进报告；
- 每个单测给 **10 秒**上限（在独立线程上跑 + 带超时地等），挂住了就跳过、不拖死整个 App。

## 五、剩下的接线（下一步）

| # | 事项 | 说明 |
|---|---|---|
| 1 | 生成器改成产出**每单测一个 `add_library(SHARED)`** | 27 个 .so，一次性生成，不手工写 |
| 2 | 跑测框架改成 **`dlopen`** 每个单测的 .so、`dlsym("main")` 调用 | 每个 .so 自己就是完整可执行体（照上游结构），**不需要给 main 改名** |
| 3 | 用 `dladdr` 取自身 .so 的目录来定位同目录下的单测 .so | 不依赖 ArkTS 传路径，自成一体 |
| 4 | 接进 App：NAPI 加 `runHostTests`、ArkTS 加按钮、cpp `CMakeLists` 引入生成的片段 | 与现有两个探针同一套路 |
| 5 | 构建 → 装真机 → 点按钮 → 读结果 | `devecocli run` + `devecocli ui layout --format json` |

**风险点（要在真机上确认的）**：OHOS 上 `dlopen` 应用自带的非 NAPI 共享库能不能成功。
原生模块本来就是这么加载的（`XComponent({libraryname:...})`），所以预期可以；
但**没验过就不算数**。

## 六、边界

- 这一步验证的是 **L1（垫片层）与 L2（宿主平台中立部分）的行为**在鸿蒙上是否正确。
- 它**不验证**：图形层（还没写）、真实游戏文件相关的东西、整条链的端到端。
- 预计会有若干单测失败——**那正是价值所在**：每一个失败都指向垫片或宿主的一个真实问题。
  失败也要如实记下来（尤其是"预期会失败"与"意外失败"要分开）。

## 二、决定性的好消息：**着色器可以 SPIR-V 直通**

上游的离线翻译链是：

```
Switch Maxwell 机器码 → (Ryujinx 翻译库，C# 工具) → SPIR-V → spirv-cross → MSL → metallib
```

**SPIR-V 恰好是 Vulkan 的原生输入。** 也就是说鸿蒙侧：
- 离线链的前半段（Maxwell → SPIR-V）**原样复用**；
- 后半段（spirv-cross 转 MSL、xcrun 编 metallib）**整段跳过**——SPIR-V 直接 `vkCreateShaderModule`；
- **少了一个工具依赖、少了一个翻译环节**（ Metal 那条路是为了迁就 Metal 才多走的）。

### 阶段 3 第一步（内存池零拷贝）——前提已验（2026-10-14 晚，真机）

探针 `vk_backend_memprobe`（App 按钮「内存池零拷贝（阶段3 前置：规模+机制）」）在 Mate 70 Pro+ 上跑通，**0 项失败**：

| 项 | 读数 |
|---|---|
| 内存堆 | 堆 0 = **15289 MiB**（显存）、堆 1 = 640 MiB |
| 候选类型 | 类型 0 = `DEVICE_LOCAL \| HOST_VISIBLE \| HOST_COHERENT`（属性 `0x7`）——**一致内存，不需要 flush** |
| ① 规模 | 64 MiB / 256 MiB / 1 GiB / 2 GiB / **3.7 GiB** 逐个"分配 + 映射 + 首中尾读写"成功（3.7 GiB 用 **1729 ms**） |
| ② 机制 | 同块内存上 A(偏移 0)/B(偏移 65536)，CPU 写 A → `vkCmdCopyBuffer` → CPU 读 B，**65536 字节逐字节一致** |
| 缓冲对齐 | `vkGetBufferMemoryRequirements` 给出 **alignment = 64**（池切片偏移要按它对） |

**结论（阶段 3 可直接用）**：

1. **零拷贝路线成立**：走"宿主自己分配"——`vkAllocateMemory`（类型 0）+ `vkMapMemory`，
   **用该地址当客体堆 `g_heap`**；`mtl_pool_add` 的对应物按 `off = mem − g_heap` 建
   `VkBuffer` + `vkBindBufferMemory`（对标 Metal 的 `newBufferWithBytesNoCopy`）。
   **不需要 `VK_EXT_external_memory_host`**。
2. 选中的类型 **`HOST_COHERENT`** ⇒ 不需要 flush/invalidate ⇒ `hle_nvn.c` 的
   `nvnMemoryPoolFlushMappedRange` 空实现**可以继续空着**。
3. **池切片绑定非零偏移可行**（实测偏移 65536），但偏移须满足缓冲的 `alignment`。

> 诚实边界：3.7 GiB 是在**没有其它图形资源共存**时分配的。堆 0 有 15 GiB、余量充足，
> 但真接入游戏后要与其它分配共存，届时需复看。

#### 3.1-A 池零拷贝原型 —— 真机通过（2026-10-14 晚）

探针 `vk_backend_poolproto`（App 按钮「池零拷贝原型（3.1-A：池切片+设备地址）」）：
造一块 32 MiB「模拟客体堆」，从中切两个池、各建 `VkBuffer` 绑到池偏移上，**0 项失败、总耗时 39 ms**。

| 项 | 读数 |
|---|---|
| 缓冲对齐要求 | **alignment = 256**（64 KiB / 1 MiB / 16 MiB 三种大小一致；用量含 `STORAGE_BUFFER` + `SHADER_DEVICE_ADDRESS`） |
| 池切片绑定 | 池A 偏移 0、池B 偏移 2 MiB，均绑定成功（**非零偏移可行**） |
| 线性不变式 | 两个池的 **GPU − CPU = 0**（完全恒等）⇒ `mtl_gpu_addr` 的 `gpu = pool.gpu + off` 成立 |
| GPU 实际读写 | CPU 写池 A → `vkCmdCopyBuffer` A→B → CPU 读池 B，**262144 字节逐字节一致**（4 ms） |

**两条要记的**：

1. **对齐要求随用量变**：只带 `TRANSFER_*` 时是 64，加上 `STORAGE_BUFFER` / `SHADER_DEVICE_ADDRESS`
   后是 **256**。池偏移必须按"实际用量查出来的 `alignment`"对齐（游戏的分配器给的是页对齐，天然满足）。
2. 本设备上 `GPU − CPU` **恰好是 0**，但**不能把它当常量依赖**——实现里仍按"同一堆内差值为常数"
   这个不变式做反查（上游 `mtl_gpu_addr` 就是这么写的）。

#### 3.1-B 客体堆预留（真实尺寸）—— 真机通过（2026-10-14 晚）

**动手前发现一个结构性问题**：客体堆是在**游戏启动时**（`SetHeapSize`）就要的，那时图形层还没初始化；
而 `VkDeviceMemory` 绑定在某个 `VkDevice` 上，**堆必须与将来的图形层用同一个设备**
⇒ **设备必须早于游戏存在**。于是新增 `dm/ohos/vk_ctx_ohos.c`：**全进程唯一、按需创建**的
共享 Vulkan 上下文 + 客体堆预留（首个使用者很可能就是堆）。这也是 `nvn_vk.c` 将来要接的那个上下文。

探针 `vk_backend_heapreserve`（App 按钮「客体堆预留（3.1-B：4GB + 池切片）」）走的就是
`hle_svc.c` 在 `DM_VK_HEAP=1` 时会走的那条路（**同一份代码，不是复制品**）：

| 项 | 读数 |
|---|---|
| 预留 | **4096 MiB**，CPU 映射 `0x6dfffff000`，耗时 1377 ms |
| 池切片 | 偏移 1 GiB / 1 GiB+64 MiB，均绑定成功 |
| 线性不变式 | 两池 **GPU − CPU = 0**，差值相同 |
| GPU 实际读写 | 1048576 字节逐字节一致（12 ms） |

总耗时 1518 ms，**0 项失败**；**既有探针复跑全部不回归**（冒烟 / SPIR-V 直通 / 内存池 / 3.1-A 各 0 败）。

**宿主侧接线**（`dm/host/hle_svc.c`，全部 `#if defined(__OHOS__)` 分叉、苹果侧逐字符不变）：

- `mem_init`：`DM_VK_HEAP=1` 时堆换成 `dm_ohos_heap_reserve()`（别名区 / 栈区仍照旧 mmap）；
- `SetHeapSize`：跳过 `mprotect`（Vulkan 内存整块一分配就是已映射可读写的）；
- `QueryMemory` 空闲分支 / `I_AslrSize` / `svc_guest_range`：报给 SDK 的区间从 5 GB 缩到 **1 GB**（别名 + 栈）。

**缺省关闭**：宿主还没能整批链接进 App，这条路没法在真机上验证 ⇒ 默认走原路，
**改错了也影响不到现有行为**；等待办 #2（真实构建链出 `libdmohos.so`）走通后再打开验。

#### 3.1-C 池模块（`nvn_vk.c`）—— 真机通过（2026-10-14 晚）

新增 `dm/gfx/nvn/nvn_vk.{c,h}`：**鸿蒙侧回放层的第一个文件**（对标 `nvn_mtl.m` 的池那部分）。
对外四个函数，与上游一一对应：`nvn_vk_pool_add` / `nvn_vk_pool_del` / `nvn_vk_addr` / `nvn_vk_gpu_addr`。

探针 `vk_backend_poolmod`（按钮「池模块（3.1-C：登记+反查+搬运）」），真机 **0 项失败、978 ms**：

| 判据 | 读数 |
|---|---|
| 池登记 | 池A 堆偏移 `0x40000000`（1 GiB）、池B `0x44000000`（1 GiB+64 MiB），各建 VkBuffer 绑成功 |
| 地址反查 | 池A+4096 → 命中、偏移 4096、设备地址 `0x6e40000000`；池B+8192 → 命中、偏移 8192 |
| 未登记区间 | 堆头部 → **命中 0**（不误报） |
| GPU 真搬运 | 按反查结果 `vkCmdCopyBuffer(A+4096 → B+8192)`，**1048576 字节逐字节一致**（13 ms） |
| **负向判据** | 堆外的内存 → **按预期被拒**（不会悄悄退化成不可用内存） |

**与 Metal 的两处刻意不同（写进了文件头）**：

1. **没有"驻留集 / 按需驻留"**——那是 iOS `MTLResidencySet` 的语义（把整池钉成 wired、不计入 footprint）。
   Vulkan 没有这个概念，内存一分配就在 ⇒ **整块省掉，不是漏了**。
2. **零拷贝不靠"套壳"**，靠客体堆本身就是 Vulkan 内存 ⇒ 池登记只是"建 VkBuffer + 绑偏移"，全程无拷贝。

**已知未做**：贴图要 `VkImage`，而 Vulkan 不允许缓冲与图像**同时**占同一段内存（`bufferImageGranularity`）
⇒ "池里同时住缓冲和贴图"留到贴图那一步单独设计。本步只覆盖"缓冲"。

**顺带发现的一个小问题**：探针按钮已到 9 个，报告 Text 被挤出可视区（真机上得从 hilog 读）。
按钮布局要收一下，留作待办。

#### 3.2 回放层最小闭环 —— 真机通过（2026-10-14 晚）

`nvn_vk.c` 长出**回放骨架**（对标 `mtl_exec`）：命令分发 + 状态累积 `S` + 管线缓存（`pso_get` 的
Vulkan 版）+ 渲染通道（传统 renderPass）+ 绘制（顶点缓冲走 3.1-C 的 `nvn_vk_addr` 反查）。

探针 `vk_backend_replay`（按钮「回放最小闭环（3.2：命令流→出图）」）：**手写一段 NVN 命令流**
（`nvn_obj.h` 的记录格式）交给 `nvn_vk_exec` 回放，离屏读回逐像素验证——**0 项失败、1638 ms**：

| 项 | 读数 |
|---|---|
| 命令流 | 1360 字节、**10 条命令、未处理 0 条** |
| 回放统计 | 绘制 1 次 / 新建管线 1 / 命中缓存 0 |
| 三角形内 (32,16) | 读到 `(0,0,255,255)`，预期蓝 ✅ |
| 三角形外 (0,63) | 读到 `(255,0,0,255)`，预期红 ✅ |

判据与阶段 2 **逐像素相同**，区别是这次画面是**从记录流回放出来的** ⇒「记录流 → 回放 → 出图」这条链通了。
回归抽查：冒烟 / 3.1-A / 3.1-C 各 0 败。

**着色器解析接缝**：回放层不自己读表，而是调 `nvn_vk_set_shader_resolver()` 装进来的回调
（"控制段哈希 + 阶段 → SPIR-V"）。探针喂阶段 2 那两条 SPIR-V；**生产实现要读的离线 SPIR-V 表还不存在**
（要靠游戏文件生成，属 L3/离线）——留缝之后两边互不阻塞。

**⭐ 一条重要的设计结论（勘测所得）**：上游对**平铺贴图并非零拷贝**——`nvn_mtl.m` 里平铺贴图一律
`newTextureWithDescriptor` **自建（自带分配）**，再把池里的字节传进去；只有
`NVN_TEXTURE_FLAGS_LINEAR` 的贴图才走 `newTextureWithDescriptor:offset:bytesPerRow:` 那种
"缓冲 + 偏移"。这正是上游要统计"贴图上传 / 重传"的原因。**Vulkan 侧照抄"自建图像"**：
既忠实于上游，又顺带避开了"线性缓冲与平铺图像不得重叠"（`bufferImageGranularity`）那条别名规则。

**本步未做**（逐步补）：索引绘制、多渲染目标、深度模板附件、贴图绑定、同步对象/事件/计数器、
按拓扑分的管线缓存（现在管线统一按 `TRIANGLE_LIST` 建）。

**顺带修掉**：探针按钮到 10 个后报告被挤出屏幕 ⇒ 页面改成**按钮区与报告区各自可滚动、各占一半**。

#### 3.2 增强 —— 正确性修补 + 测量骨架（2026-10-14 深夜）

**为什么先做这两件**：① 3.2 埋下了三类"**不报错的错**"，不补掉后面所有性能对照都在比错的东西；
② "以性能优化为标准"的前提是**能说出这一步花了多少 GPU 时间、搬了多少字节**——没有测量，优化只能靠感觉。

| 项 | 内容 |
|---|---|
| **拓扑进管线键** | 3.2 里管线一律按 `TRIANGLE_LIST` 建，真实拓扑被 `(void)topo` 丢掉 ⇒ 换拓扑会**静默复用错管线**。已把拓扑加进 `vk_pso_key`。 |
| **索引绘制** | `OP_DRAW_IDX` 补上（索引缓冲同样走池反查；偏移按索引宽度校验）。 |
| **绑定槽位 `first≠0`** | `OP_BIND_VATTR` / `OP_BIND_VSTREAM` 原先只认 `first == 0`，非 0 起点被**静默忽略**；改为按槽位写入并取高位计数。 |
| **测量骨架** | `nvn_vk_stats_t`：命令 / 未处理 / 绘制 / 通道 / 管线新建与命中、附件读入写出字节（估算）、**整帧与逐通道 GPU 耗时**（时间戳查询；`timestampValidBits` 在**队列族**属性里，不在物理设备属性里）。 |

探针实测（命令流 12 条）：绘制 3 次 / 通道 1 / **新建管线 2、命中缓存 1**（索引绘制复用三角形管线、
线带另建一条 ⇒ **拓扑确实进了键**）/ 未处理 0 条；**GPU 耗时 0.072 ms（通道 0：0.053 ms）**；
附件写出 16.0 KiB（64×64×4，对得上）。像素判据仍与阶段 2 逐像素一致。

> **回归**：Vulkan 冒烟 0 败。3.1-C 的回归**未跑完**——设备中途被切到了别的应用（我没有继续动它）。
> 本步没有触碰 3.1-C 的代码路径（池登记 / 地址反查），风险为零，但**如实记为"未验"**。

**下一步（按"性能为标准"重排后的顺序）**：管线缓存落盘（`VkPipelineCache` 序列化——Metal 没有的能力）
→ 贴图（GPU 转码 BC→ASTC）→ 出图 + 可变帧率节拍（`OH_DisplaySoloist`）。

#### 管线缓存落盘 —— 真机通过（2026-10-14 深夜）—— **第一项"鸿蒙特有优化"**

**为什么这是"上游做不到"的一项**：`VkPipelineCache` 可以序列化到盘上，第二次启动直接命中 ⇒ 零编译。
上游 Metal 侧只有"离线 metallib + 预热清单"（**构建期**产物），**做不到运行时积累**。

探针 `vk_backend_psocache`（按钮「管线缓存落盘（冷/热对照）」）：同一段命令流跑两轮，各 3 遍
（每遍清掉内存里的管线表 ⇒ 逼它真的重建管线），**0 项失败**：

| 轮次 | 建管线 | 累计耗时 | 载入缓存 |
|---|---|---|---|
| ① 冷启动（空缓存） | 6 条 | **37.033 ms** | 0 字节 |
| ② 热启动（载入刚存盘的缓存） | 6 条 | **0.377 ms** | 2956 字节 |

⇒ **省 99%**。缓存文件 2956 字节，落在应用数据目录 `filesDir/vk_pso_cache.bin`。

**顺带修掉两个测试自身的问题**（都不是产品缺陷，但会误导判断）：

1. `pso_cache_blob` 原先放在统计结构里，`frame_begin` 的 `stats_reset` 一清就变 0 ⇒ 判据误报"没载入"。
   已把它移出统计结构（它由"打开缓存"决定，与每帧统计无关）。
2. 3.2 探针的判据"新建管线应为 2"**依赖运行顺序**：先跑过落盘探针后，管线表已被填满 ⇒
   这里命中缓存 3 次、新建 0 条，误报失败。已在 3.2 探针开头显式 `nvn_vk_pso_local_clear()`。

#### 3.3-B 可变帧率节拍（`OH_DisplaySoloist`）—— **已实现，待真机读数**

**为什么做**：3.3-A 量的是"裸 present 的节拍上限"——自己埋头连画 60 张，每帧还 `vkQueueWaitIdle`
等 GPU 干完。它回答不了真正要紧的事：**屏幕的拍子是什么样**、**能不能按负载降帧**、**回调里能不能做重活**。
`OH_DisplaySoloist`（官方组件，API 12 起）就是鸿蒙给的"报时员"：每次 VSync 到来时系统调我们的回调，
并把**本拍与下一拍的时间戳**一并告诉你。

**动的手脚**（`dm/ohos/vk_backend.c` + napi + 页面 + CMake）：

| 项 | 内容 |
|---|---|
| 抽出共用骨架 | `os_setup` / `os_frame_do` / `os_teardown` + `os_slot`（槽位：命令缓冲+栅栏+两信号量）。3.3-A 改为调用它们，**行为与首次通过时同一套口径**（单槽位、每帧等 GPU） |
| 新增探针 | `vk_backend_pace()`，按钮「可变帧率节拍（3.3-B：DisplaySoloist 5 组对照）」 |
| 5 组同轮对照 | ① 裸 present·等 GPU（3.3-A 老基线）② 裸 present·不等 GPU（上游语义）③ DisplaySoloist 60Hz·不等 GPU ④ 同 60Hz·等 GPU ⑤ DisplaySoloist 30Hz·不等 GPU。**自带对照是为了同一轮里比**——跨轮次比读数会漂 |
| 新增依赖 | `libnative_display_soloist.so`；头文件在子目录，须 `#include <native_display_soloist/native_display_soloist.h>` |
| 三个判据 | ① 回调间隔 ≈16.67 ms（系统报时成立）② 设 30fps 后间隔翻倍 ≈33.3 ms（可变帧率生效）③ 回调里等 GPU 是否拖垮节拍（④ vs ③） |
| 顺带量三项 | 回调线程 id（是不是另起一条线程）、回调单次耗时、我们出图的节奏 → 决定生产形态怎么接 |

**两处刻意的写法**（都有理由，不是随手写的）：

1. **`stop` → `Stop` → 等回调退出 → `Destroy`** 这个收尾顺序不能省：`OH_DisplaySoloist_Stop` 只保证
   "不再请求下一拍"，**不保证当前这一拍已经退出来**。直接 Destroy 就是"回调还在碰已销毁的 Vulkan 对象"。
2. **等拍用轮询 + 超时**（不是死等信号量）：探针宁可如实报"没收到应有的拍数"，也绝不把 App 挂死。

**生产形态已定（探针里为何仍按"回调里出图"写）**：节拍器 `nvn_pace.h` 的唯一使用者是
**`hle_nvn.c` 第 1187 行——接口层**，也就是"平台中立、原样复用"的那一层；上游在旁注明了语义
**"出图只入队、立即返回；本帧显示时刻按节拍器排"**。所以生产形态是：**DisplaySoloist 只当报时源**
（回调提供时间戳），渲染与 present 仍归游戏线程，接口层一个字不动。把渲染搬进回调就得改 `hle_nvn.c`，
与节拍器抢方向盘 —— 探针里之所以仍按"回调里出图"写，是因为探针没有游戏线程、没有接口层，只能这么量。

**真机读数（2026-10-15，Mate 70 Pro+ `3EV0224B19015395`）—— 失败 0 项，总耗时 5.3 s**

先立两条前提，否则数字会被误读：

| 前提 | 读数（`hidumper -s RenderService -a screen`） |
|---|---|
| 面板支持的刷新档位 | **120 / 90 / 72 / 60 / 45 / 40 / 36 / 30 Hz**（八档） |
| `activeMode` | 跑之前 60 Hz；两次复跑之间读到 **120 Hz** ⇒ **面板在动态换档** |
| 提交的呈现模式 | **FIFO**（枚举值 2；探针原先把这行标成"队列"是错的，已修） |

| 组 | 出的帧／收到的拍 | 系统给的拍子（最小/平均/最大 ms） | 我们出图的节奏（平均） | 回调单次耗时（平均/最大） |
|---|---|---|---|---|
| ① 裸 present·等 GPU | 60 帧 | —（无系统拍子） | **5.46 ms ≈ 183.2 fps** | — |
| ② 裸 present·不等 GPU | 60 帧 | — | **5.54 ms ≈ 180.5 fps** | — |
| ③ DS 60Hz·不等 GPU | 60 拍 | 21.98 / **22.51** / 33.45 | 22.44 ms ≈ 44.6 fps | 3.26 / 6.98 ms |
| ④ DS 60Hz·等 GPU | 60 拍 | 8.29 / **20.76** / 22.36 | 20.76 ms ≈ 48.2 fps | 2.91 / 6.14 ms |
| ⑤ DS 30Hz·不等 GPU | 60 拍 | 33.46 / **33.49** / 34.12 | 33.44 ms ≈ 29.9 fps | 3.31 / 5.28 ms |

**三个判据 + 两条关键旁证**

- ① ⚠ **60fps 这个请求没被满足**：实得 22.51 ms ≈ 44.4 fps，**正好落在受支持的 45 Hz 档**上；
  且两组 60Hz 都飘（min 8.29/21.98、max 33.45/22.36），而 **30Hz 组稳得像钉住**（33.46–34.12，抖动比 1.02）。
  ⇒ 形状像"**面板在换档**"，不像"回调没来"。**先查清再定回放层怎么接它。**
- ② ✅ **帧率可设、而且准**：设 30fps ⇒ 实测 33.49 ms（理论 33.33），几乎精确命中。
- ③ ✅ **回调里等 GPU 没拖垮节拍**（20.76 vs 22.51 ms，×0.92）—— 回调本身只要 ~3 ms，远小于 22 ms 的间隔。
  但**仍不建议**生产在回调里等 GPU（理由见上「生产形态已定」）。

> ⭐ **本轮最值钱的一条（比 3.3-B 本身重要）**：**FIFO 在这台设备上并没有把出图节流到刷新率**——
> 裸 present 两组平均间隔只有 5.46 / 5.54 ms（**≈183 fps**），远超任何一档刷新率，说明 present 返回得很快、
> 帧被排掉或替换，而不是被 vsync 限住。⇒ **"靠 present 自动限速"这个假设在鸿蒙上不成立**；
> 要节拍就必须自己排 —— 这正是 DisplaySoloist 的价值所在。
>
> 另一条新事实：**回调确实跑在系统另起的一条线程上**（回调线程 id ≠ 主线程），不在 UI 线程。
> 抖动比（最大/平均）：裸 present 不等 GPU **1.71** ／ DisplaySoloist 60Hz **1.37** ⇒ 系统给的拍子更整齐。

**3.3-A 复跑回归（换过骨架，必做）**：✅ **全部通过、失败 0 项**（345 ms，present 59 帧，约 183 fps）。
报告里 setup 各行齐全 ⇒ 顺带确认下面那个真 bug 已修。

**顺带修掉的一处真 bug（同类教训：不报错的错最贵）**：报告出口 `os_emit` 原先**按值**传给助手函数，
于是每层改的是自己的游标副本 —— 各层输出全落在**同一个偏移**上互相覆盖。真机表现：**报告只剩首尾两块、
中间 5 组的明细整段消失，且不报任何错**（3.3-B 第一次真机跑就是这么栽的：判据块把 5 组明细整段盖掉）。
改成按指针传递即修复。

#### 3.3-B 遗留问题「请求 60fps 实得 22.5ms」—— **已定性：不是缺陷，是系统决策**

**实验（零代码改动）**：跑探针的同时，从主机侧轮询面板档位
（`hdc shell "hidumper -s RenderService -a screen"` 的 `activeMode`），拿到一条时间线：

| 采样 | `activeMode` | 对应时段 |
|---|---|---|
| 1–2 | 60 Hz | 跑之前 |
| **3–6** | **90 Hz** | **正好覆盖 ③④ 两组「请求 60fps」的窗口** |
| 7–20 | 60 Hz | 之后回落（⑤ 请求 30fps 那段） |

**算得通**：90 ÷ 2 = 45 fps = 22.2 ms ≈ ③ 组实测 **22.71 ms**（④ 组最小 16.74 ms = 60 Hz 的一拍，
说明中途短暂回到过 60 档）。

**官方定性**（《可变帧率简介》开发指南，原文）：

> 开发者通过设置有效的期望绘制帧率后，系统会收集设置的请求帧率，进行决策和分发，**在渲染管线上进行分频**，
> 尽量能够满足开发者的期望帧率。
> **约束与限制：开发者设置的期望帧率值不能代表最终实际效果，会受限于系统功耗性能约束和屏幕刷新率硬件能力限制。**

⇒ **期望帧率是"建议"，不是"命令"**：系统先定整机刷新率档位，再在渲染管线上分频。
请求 30 那组恰好被满足（60 ÷ 2 = 33.3 ms），是"系统那次的决策正好等于你要的"，不是"设 30 就一定有 30"。

**对回放层的两条硬结论**（与前面"FIFO 不限速"合起来，指向同一个设计）：

1. **不能假设回调按你设的帧率来** ⇒ 节拍必须**自己排**（上游 `nvn_pace.h` 那套正是干这个的），
   DisplaySoloist 只当 **vsync 报时源**；
2. 真在意某个帧率，要顺着"整机刷新率决策"的思路做，而不是死守 `expected`。

#### 3.3-C 帧率接入口对照（DisplaySoloist vs XComponent 侧）—— 真机跑到一半，**结论已经很清楚**

**为什么做**：官方"可变帧率"有四个接入口，其中 **XComponent 侧那一条（API 11 起，
`OH_NativeXComponent_SetExpectedFrameRateRange` + `RegisterOnFrameCallback`）更贴合"游戏渲染进 XComponent"**，
与 3.3-B 用的 `DisplaySoloist` 二选一需要实测。

**结果（Mate 70 Pro+，2026-10-15；定稿读数来自修正后的一轮：失败 0 项、5563 ms）**：

| 组 | 收拍 | 系统给的拍子（最小 / 平均 / 最大 ms） | 回调线程 |
|---|---|---|---|
| ① DisplaySoloist 60Hz | 60 拍 | 21.93 / **22.33** / 22.38（≈44.8 fps） | 系统另起线程 |
| ② DisplaySoloist 30Hz | 60 拍 | 8.22 / **32.69** / 33.68（≈30.6 fps） | 系统另起线程 |
| ③ DisplaySoloist 60Hz · **等 GPU** | 60 拍 | 16.75 / **16.75** / 16.75（**≈59.7 fps，最小=平均=最大**） | 系统另起线程 |
| ④ **XComponent 侧 60Hz** | **0 拍** ← 一次回调都没来 | — | —（按官方：在 UI 主线程） |

> ⭐ **① 与 ③ 请求的是同一个帧率（60），却分别落到 44.8 fps 与 59.7 fps** ⇒
> **系统的帧率决策不是确定性的**（面板档位/功耗/热状态都在参与）。这一条把"节拍必须自己排"钉死了：
> 同一个请求在同一个应用里都能给出两个不同的结果，任何依赖它的设计都不成立。
>
> （③ 的极小=平均=极大=16.75 ms，是这一轮唯一一次拿到**精确 60fps** 的记录 ——
> 但它是**碰上的**，不是设出来的，不能当能力用。）

**根因（两条独立证据互相印证）**：

1. **官方明文**（《请求自绘制内容绘制帧率》）：**"回调函数运行于 UI 主线程"**，且
   **"从 API version 18 开始……只在 XComponent 上树期间能收到期望回调"**（本机 API 26 ⇒ 按 18+ 行为）。
2. **真机证据**：探针是**同步阻塞 UI 线程**等拍的 —— 而 XC 侧回调偏偏要在 UI 主线程上派发，
   UI 线程被自己堵住，回调就永远投递不进来 ⇒ **0 拍**。

**⭐ 顺带撞到一个必须记的系统行为**：三个 XC 组各等 5 秒超时，UI 线程被堵了 20 秒 ⇒
系统判定 **`THREAD_BLOCK_6S`，App 被 `PROCESS_KILL` 杀掉**（系统日志原文：
`appFreeze happend, eventName: APP_INPUT_BLOCK` → `[FRAMEWORK,PROCESS_KILL] reason=THREAD_BLOCK_6S`）。
⇒ **探针（以及将来的游戏）都不许把 UI 线程堵超过 ~5 秒**；3.3-B 之所以活着，是因为它总共只堵 5.4 秒。
**已修**：XC 组只短等 1.2 秒（原理上收不到，够确认即可），整轮回到 5.56 秒 ⇒ 不再触发看门狗。

**这一轮已经得出的交付结论**：**两条入口不是"同源的两个门面"，它们在回调线程模型上有实质差别**：

| | `DisplaySoloist` | XComponent 侧接口 |
|---|---|---|
| 回调线程 | **系统另起的独占线程**（真机实测） | **UI 主线程**（官方明文） |
| 对游戏（渲染在主循环线程、不能堵 UI） | **合适** | 不合适 |
| 实例生命周期 | 要自己 Create/Destroy | 随 XComponent 组件走 |

⇒ **生产接入口选 `DisplaySoloist`**（3.3-B 已验证：独立线程、帧率可设、回调 ~3 ms）。

**仍未做（要才能把 XC 侧量出数）**：XC 那条要真正读数，必须把探针改成**两段式**——
按钮一「注册后立即返回」（把 UI 线程让出来），回调在 UI 线程上自己出图收拍；
按钮二「取结果」。**同步阻塞式探针在原理上就测不到它。** 是否值得为此再改一轮，见待办。

**四个接入口备查**：`expectedFrameRateRange`（ArkUI）、`displaySync`、
`OH_NativeXComponent_SetExpectedFrameRateRange` + `RegisterOnFrameCallback`（API 11，随 XComponent）、
`DisplaySoloist`（本步选用）。回调签名两边都是 `(timestamp, targetTimestamp)`。

#### 3.4 贴图（BC→ASTC + 上传）—— 开工前先把拆法做实（勘测所得，2026-10-15）

**为什么要先勘测**：原来只知道"设备不支持 BC、要用计算着色器转码"。把上游 `dm/gfx/tex/` 读完之后
发现**上游对"设备没有 BC"这件事本来就有两轨方案，而且已经有一个 GPU 计算着色器的先例** ——
拆法和取舍都跟着变了。

**上游贴图层有什么（逐文件勘测）**：

| 文件 | 是什么 | 对鸿蒙意味着什么 |
|---|---|---|
| `tex/nvn_bcdec.c`（58 行） | **CPU 解 BC**（bcdec 的封装）。上游**就是给"没有 BC 的 GPU"（苹果 A15/A16）用的** | **平台中立、可直接复用** —— 我们的情形与它一字不差 |
| `third_party/bcdec/` | 单头文件 BC 解码器（MIT / 公有领域） | 直接复用，零改动 |
| `tex/nvn_deswizzle.c`（71 行） | **Tegra 块线性 ↔ 线性**，还带反向 `nvn_swizzle`（给单测做往返） | **平台中立、可复用**；已有"往返逐字节 + 逐点偏移对手算"两种判据可照搬 |
| `tex/nvn_deswizzle_gpu.m` | **Metal 计算着色器的 GPU 版解排布** | ⭐ **上游已有"GPU 做贴图变换"的先例** ⇒ 我们的 GPU 转码不是凭空发明 |

| `tools/astc_pack.py` | **离线**把游戏贴图里的 BC3 转成 ASTC（"老机型补充包"） | 上游的第二轨；要核实它能否脱离苹果链独立跑 |
| `tex/tests/`（`t_tex.c` + `fetch_samples.py`） | 上游贴图测试与样本拉取 | 有现成判据与样本可用 |

**⇒ 修订后的三步拆法**（每步都有自己的真机判据）：

**3.4-A 贴图通道最小闭环** —— 三条路都要它，先做
1. CPU 用 `nvn_bc_decode` 解一张 BC 贴图 → RGBA8 =**参照**
2. 自建 `VkImage`（照抄上游"平铺贴图一律自建图像"的做法）+ 上传 + 采样（管线加采样器/描述符）
3. **判据**：读回像素与 CPU 解码结果**逐像素一致（±1）**—— 两条独立路径互证
4. 交付：把"图像创建 → 上传 → 描述符 → 采样"这条通道打通

**3.4-B 块线性解排布** —— **接真贴图的硬前置，必须早于接真场景**
- 复用 `nvn_deswizzle.c`（平台中立）；判据照搬上游：往返逐字节一致 + 逐点偏移对手算

**3.4-C BC→ASTC 转码** —— **这里有三条路，需要用户裁决**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **C1 忠实上游** | 运行时 CPU 解 BC → 上传**未压缩** RGBA8 | 零新算法，`nvn_bcdec.c` 直接复用，当天能验 | **显存/带宽翻 4–8 倍**（BC1 是 0.5 B/px，RGBA8 是 4 B/px） |
| **C2 上游第二轨** | **离线**把 BC3 → ASTC（重跑 `astc_pack.py` 那条链） | 显存最优、运行时零成本 | 要改打包链；脚本原为苹果老机型写的，能否独立跑未核实 |
| **C3 文档原计划** | **GPU 计算着色器 BC→ASTC** | 显存最优 + 运行时零 CPU 成本；上游有 GPU 变换先例 | 要在着色器里同时写 BC 解码与 ASTC 编码，工作量最大、风险最高 |

> **倾向**：**A → B → 先 C1（最快让真贴图跑起来）→ 再 C3（当作第二项"鸿蒙特有优化"替换掉 C1）**。
> 理由：C1 零新算法、拿真场景当天就能验证；C3 是新算法，**等真场景跑起来、有真实带宽/显存读数之后再投入**，
> 才是"先有可跑的、再有快的"这个项目一贯的节奏。C2 的另一条价值是：如果打包链能独立跑，
> 它可能比 C3 更省事（离线一次性成本，运行时零成本）。

## 四、鸿蒙 NEXT 特有游戏机制的接入点（按阶段落位）

> 其余要么是"上架运营"才需要的（登录/支付/广告/运营），要么要等真游戏跑起来才有意义（超帧/ABR/秒级启动）。
> 另注：图形加速服务**模拟器不支持**（我们本来就走真机），系统能力 `SystemCapability.Graphics.Accelerate`。
> **诚实边界**：它的**接入条件**（是否要上架/白名单/AGC 配置、权限怎么开）尚未核实 —— 要推进时先查清再定。

> 侦察证据：`$NDK/sysroot/usr/include/vulkan/vulkan_ohos.h`（`VkSurfaceCreateInfoOHOS.window: OHNativeWindow*`）、
> `vulkan_core.h` 的 `VK_STRUCTURE_TYPE_*_OHOS` 系列（surface / native buffer 导入 / swapchain image）。
> 另：NDK **没有** shaderc/glslang ⇒ 阶段 1 的三角形并入阶段 2（SPIR-V 直通一起验，编译在电脑侧解决）。

## 五、需要早查的三个前提（阶段 1 期间顺带查）

1. **OHOS 的 Vulkan WSI**：`libvulkan.so` 有没有 `VK_OHOS_surface` 扩展（决定阶段 4 是走标准 swapchain 还是离屏 blit 到 XComponent）；
2. **BC→ASTC 的取舍**：设备不支持 BC ⇒ 转码放离线（构建期）还是运行时（首载慢一点但不用改链）；
3. **`nvn_thunks.S` 的再生成**：生成器在哪、OHOS 侧要不要 `CSYM` 一类的宏（有 `nvn_entry.S` 的先例可抄）。

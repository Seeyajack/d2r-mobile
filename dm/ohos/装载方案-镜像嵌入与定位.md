> 状态：**设计已由真机实验验证**

## 零、结论摘要（先看这段）

**真机实验推翻了我们原先的假设，而且结果对我们有利。**

| 实验 | 预期 | **实测** | 影响 |
|---|---|---|---|
| **D** 完整链路（嵌入→定位→映射→执行） | — | ✅ **通了** | **装载机制在真机上端到端成立** |
| **A** 匿名内存能否可执行 | 失败 | ✅ **成功，而且真能执行** | **桌面版 `map_image()` 的写法可以直接用** |
| **B** `mmap` 文件能否可执行 | 成功 | ❌ **失败（Permission denied）** | 原设计（照搬 iOS 的文件映射）**不需要了** |
| **C** 自定义段 + `__start_/__stop_` | 能 | ✅ **能** | 用来**定位**嵌入的镜像 |

**修订后的方案（比原设计简单得多）：**

1. **嵌入**：把镜像作为自定义 ELF 段放进 `.so`（实验 C 验证可用）
2. **定位**：用链接器生成的 `__start_/__stop_` 符号拿到它在内存里的地址（实验 C ✅）
3. **映射**：`mmap` 匿名内存 → `memcpy` 把镜像拷进去 → `mprotect` 代码段成 R+X（实验 A ✅）
   —— **这就是上游桌面版 `map_image()` 的原样做法，一行都不用改思路**
4. ~~文件映射 + `MAP_FIXED` 摆位置~~ —— **不需要**（实验 B 证明鸿蒙根本不允许）

> **为什么 A 能过**：鸿蒙禁的是**可写又可执行的匿名内存**（W+X，防 JIT）。
> 我们要的是**只读+可执行**（R+X），不在此列。实测证实了这一点。

## 一、iOS 是怎么做的（背景，读代码得到的事实）

### 嵌入（`dm/ios/tools/gen_embed.py`）

把改写后的游戏映像切成三块，用汇编 `.section` 放进可执行文件：

| 段 / 节 | 装什么 |
|---|---|
| `__TEXT,__dm<名>x0` | 原 text（**代码**） |
| `__DM<名>W,__img` | 中间的 ro + data + bss（**可写数据**） |
| `__TEXT,__dm<名>x1` | 补丁区（**代码**） |

### 运行时映射（`loader.c` 第 311 行，`TARGET_OS_IPHONE` 分支）

```
1. getsectiondata(&_mh_execute_header, "__TEXT", "__dm<名>x0", &z0)   ← 取三块的地址与长度
2. vm_allocate(一整块连续地址)
3. vm_remap 把三块按原相对位置放回去：
     代码块  copy = FALSE   → 与已签名页共享同一批物理页（因此是 r-x）
     W 块    copy = TRUE    → 写时复制
```

**为什么绕这么大一圈**：iOS 不许运行时装入的代码执行，也不许匿名内存可执行。
唯一合法的"可执行内存"是**从文件里映射出来的、已签名的页**。

### 桌面版（`#else` 分支，第 341 行）

```c
m->base = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANON, -1, 0);
memcpy(m->base, raw, sz);
mprotect(m->base, rx, PROT_READ | PROT_EXEC);          // 代码区
mprotect(m->base + po, ..., PROT_READ | PROT_EXEC);    // 补丁区
```

**这段就是鸿蒙该走的路。**

## 二、真机实验结果（2026-10-13，HUAWEI Mate 70 Pro+，API 26）

实验代码：`dm/ohos/app/entry/src/main/cpp/dm_probe.c`

### 实验 D：完整链路 —— ✅ 通了（最重要的一条）

用 `dm/ohos/tools/gen_embed_ohos.py` 把一份**带真实可执行代码的测试映像**编进 `.so`，
再让 `dm/ohos/map_image_ohos.c`（就是宿主 `loader.c` 会调用的那一份）走完整流程：

```
【实验 D】完整链路：嵌入 → 定位 → 映射 → 执行
鸿蒙装载 main：base 0x5b6d60d000 size 49152（x0 16384 / w 16384 / x1 16384，页 4096）
  ✓ 定位 + 拷贝：base 0x5b6d60d000，size 49152
  ✓ 数据段："DM_OHOS_IMAGE_OK"
鸿蒙装载 main：代码区已封为 R+X（text 16384 字节，补丁区从 +0x8000）
  ✓ 代码区已封为只读+可执行
  ✓ 执行映像代码：返回 0x1234（期望 0x1234）
  结论：整条链路通了 —— 嵌入/定位/映射/执行全部成立。
```

测试映像（`test_image.S`，由 `gen_embed_ohos.py --embed-bytes` 生成，仅 21 行）：
| 映像偏移 | 内容 |
|---|---|
| 0x0000 | 代码 `mov w0, #0x1234 ; ret` |
| 0x4000 | 数据 `"DM_OHOS_IMAGE_OK"` |
| 布局 | TEXT_END 0x2000 / 键页 0x4000 / PATCH_OFF 0x8000 / 共 0xC000 |

**这证明了：三块自定义段能正确拼回原映像布局、映射后代码真的能执行、数据真的能读到。**

### 实验 C：自定义段 + 链接器符号 —— ✅ 通过

```
【实验 C】自定义 ELF 段能否生成 __start_/__stop_ 符号
  __start_dmprobesec = 0x5b97100f60
  __stop_dmprobesec  = 0x5b97100f81
  段长度 = 33 字节
  段内容前 16 字节：DM_PROBE_MARKER_
  ✓ 符号可用，内容与标记匹配
  结论：嵌入用「自定义段 + 链接器符号」可行，不必自己解析 ELF 头。
```

**做法**：
```c
__attribute__((section("dmprobesec"), used))
const char dm_probe_marker[] = "DM_PROBE_MARKER_0123456789ABCDEF";

extern const char __start_dmprobesec[];
extern const char __stop_dmprobesec[];
```
段名必须是合法的 C 标识符，链接器才会生成那对符号。

### 实验 B：文件映射成可执行 —— ❌ 失败

```
本模块 .so 路径：/data/storage/el1/bundle/libs/arm64/libdmprobe.so
✗ B-1 mmap bundle 里的 .so 成 R+X：失败（Permission denied）
✗ B-3 mmap 数据目录文件成 R+X：失败（Permission denied）
```

**bundle 目录和应用数据目录都不许可**，所以：
- 不是"目录挂载属性"的问题，是**策略层面**禁止应用把文件映射成可执行
- **iOS 那套文件映射路线在鸿蒙上完全不可用**（原设计作废）

### 实验 A：匿名内存成可执行 —— ✅ 通过（出乎意料）

```
✓ mmap 匿名 RW：成功，地址 0x5b6c53f000
⚠ mprotect 成 R+X：成功  ← 与预期不符！
⚠⚠ 匿名内存真的可执行！桌面版写法可用，方案可以简化
```

**"真的可执行"是执行验证过的**：往页里写了一条 ARM64 `ret`（`0xd65f03c0`），
`mprotect` 成 R+X，然后**真的跳进去执行**——正常返回，没崩。

**结论**：鸿蒙禁的是 **W+X（可写又可执行）匿名内存**（防 JIT），
**R+X 匿名内存是允许的**。我们的用法正好是 R+X，所以不受影响。

## 三、修订后的设计

### 3.1 嵌入：自定义 ELF 段

```asm
.section dmmainx0, "a", @progbits    ← 代码块（先当数据放进来）
.section dmmainw,  "a", @progbits    ← 数据块
.section dmmainx1, "a", @progbits    ← 补丁区
```
新脚本：`dm/ohos/tools/gen_embed_ohos.py`（对应上游的 `gen_embed.py`）。

> 与 iOS 的差别：**不需要**把它们放进可执行段（`"ax"`）——
> 因为运行时是拷到匿名内存再改权限的，段本身只要可读就行。

### 3.2 定位：链接器符号

```c
extern const uint8_t __start_dmmainx0[], __stop_dmmainx0[];
size_t z0 = __stop_dmmainx0 - __start_dmmainx0;
```

### 3.3 映射：照抄桌面版

```c
m->size = (sz + 0x3FFF) & ~0x3FFFull;
m->base = mmap(NULL, m->size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
memcpy(m->base, __start_dmmainx0, sz);                      // 从自定义段拷进来
mprotect(m->base, text_end_rounded, PROT_READ | PROT_EXEC); // 代码区 R+X
mprotect(m->base + patch_off_rounded, ..., PROT_READ | PROT_EXEC); // 补丁区 R+X
```

**这三行就是 `loader.c` 桌面分支的 `map_image()`，逻辑完全一致。**

### 3.4 强制接管表（`swforce`）

同样改成自定义段 + 链接器符号：
```c
extern const hle_force_ent __start_dmswforce[], __stop_dmswforce[];
g_nforce = (unsigned)(__stop_dmswforce - __start_dmswforce);
```
`hle.h` 的 `HLE_FORCE` 宏要从 `__attribute__((section("__DATA,swforce")))`
改成 `__attribute__((section("dmswforce")))`。

## 四、踩过的坑（写代码时注意）

| 坑 | 症状 | 原因 |
|---|---|---|
| **段符号没声明成弱符号** | 链接失败：`undefined symbol: __start_dmsdkx0` | `map_image_ohos.c` 引用三个模块的段；只嵌入部分模块时就链接不过。**必须加 `__attribute__((weak))`** —— 实测 lld 行为：段存在→强符号被解析；段不存在→弱引用为 0，不报错 |
| **`mprotect` 之后再写页** | 进程当场退出 | `mprotect` 成 R+X 后页不可写，再 `memcpy` 进去就是 SIGSEGV。**必须先写、后改权限** |
| **在鸿蒙 App 里 `fork()`** | 进程整个消失 | 实测 fork 会把 App 带崩。要隔离危险操作，用**信号处理器 + `siglongjmp`**，别用 fork |
| **危险实验要排在最后** | 前面的结果丢了 | 顺序改成 D → C → B → A（A 最后），万一 A 把进程搞挂，前面的已经跑完并写进日志 |
| **结果同时打 hilog** | 界面没显示就什么都看不到 | 每写一行都 `OH_LOG_Print`，进程挂了也能从日志里看出跑到哪一步 |

## 五、其他鸿蒙适配点（`loader.c` 里剩下的）

| 位置 | 问题 | 说明 |
|---|---|---|
| `tsd_check()` | **必须重做** | 用 `mrs tpidrro_el0` 并假定「槽 = tpidrro_el0 + 8×键号」—— 这是**苹果 pthread 的 TSD 布局**。musl 不同，且 Linux 上 `tpidrro_el0` 通常为 0。**整个线程槽机制要按 musl TLS 重新设计，并牵连改写器的改写目标** |
| `strlcpy` | 需确认 | BSD 函数；musl 是否提供待确认 |
| `TargetConditionals.h` | 要换 | 第 275 行 `#if TARGET_OS_IPHONE` 换成鸿蒙自己的条件 |
| `CommonCrypto` | 最后再换 | 只在 `DM_LOADHASH` 诊断路径用 |

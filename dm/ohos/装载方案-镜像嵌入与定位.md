# 装载方案 · 镜像的嵌入与运行时定位（鸿蒙）

> 第 3 站收尾成果 ｜ 编制日期：2026-10-13
> 解决的问题：`loader.c` 依赖 Mach-O（`getsectiondata`）取游戏镜像，鸿蒙没有这套机制
> 状态：**设计方案，未在真机验证**

---

## 一、先看 iOS 是怎么做的（读代码得到的事实）

### 嵌入（`dm/ios/tools/gen_embed.py`）

把改写后的游戏映像切成三块，用汇编 `.section` 放进可执行文件：

| 段 / 节 | 装什么 |
|---|---|
| `__TEXT,__dm<名>x0` | 原 text（**代码**） |
| `__DM<名>W,__img` | 中间的 ro + data + bss（**可写数据**） |
| `__TEXT,__dm<名>x1` | 补丁区（**代码**） |

每块按 16 KB 对齐。

### 运行时映射（`loader.c` 第 311 行，`TARGET_OS_IPHONE` 分支）

```
1. getsectiondata(&_mh_execute_header, "__TEXT", "__dm<名>x0", &z0)   ← 取三块的地址与长度
2. vm_allocate(一整块连续地址)
3. vm_remap 把三块按原相对位置放回去：
     代码块  copy = FALSE   → 与已签名页共享同一批物理页（因此是 r-x）
     W 块    copy = TRUE    → 写时复制
```

### 为什么绕这么大一圈

> **iOS 不许运行时装入的代码执行，也不许匿名内存可执行。**
> 唯一合法的"可执行内存"，是**文件里映射出来的、已签名的页**。
> 所以只能：把代码放进可执行文件 → 再把这些页 `vm_remap` 到想要的位置。

---

## 二、鸿蒙为什么可以用同一套思路

**鸿蒙有同一类限制**：自 5.0.0(12) 起禁止匿名内存申请可执行权限（JIT 需受限权限）。

所以桌面版 `loader.c` 的那套（`mmap` 匿名 → `memcpy` → `mprotect` 成 R+X）**在鸿蒙上行不通**——和 iOS 一样被卡住。

**但"文件映射出来的页可以执行"这条在鸿蒙上是成立的**（否则 `.so` 本身就没法跑）。

**结论：思路完全一致，只是把 Mach-O 的 API 换成 ELF 的。**

---

## 三、鸿蒙的对应设计

### 3.1 嵌入：自定义 ELF 段 代替 Mach-O 段

鸿蒙 NDK 用 **lld**，支持 ELF 的自定义段与链接器自动符号：

```
.section dmmainx0, "ax", @progbits     ← 代码块（a=可分配，x=可执行）
.section dmmainw,  "aw", @progbits     ← 数据块（a=可分配，w=可写）
.section dmmainx1, "ax", @progbits     ← 补丁区
```

对应关系：

| iOS | 鸿蒙 |
|---|---|
| `__TEXT,__dm<名>x0` | 段 `dm<名>x0`（`ax`） |
| `__DM<名>W,__img` | 段 `dm<名>w`（`aw`） |
| `__TEXT,__dm<名>x1` | 段 `dm<名>x1`（`ax`） |

**注意**：段名必须是合法的 C 标识符（不能带点），因为链接器要生成 `__start_<段名>` / `__stop_<段名>` 符号。

新脚本：`dm/ohos/tools/gen_embed_ohos.py`（对应上游的 `gen_embed.py`）。

### 3.2 运行时定位：链接器符号 代替 getsectiondata

```c
extern const uint8_t __start_dmmainx0[], __stop_dmmainx0[];   // 链接器自动生成
size_t z0 = __stop_dmmainx0 - __start_dmmainx0;
```

**不需要解析 ELF 头**——链接器直接把符号给你。

### 3.3 运行时映射：mmap 自己的 .so 代替 vm_remap

```
1. dladdr(某个本 .so 内的符号) → 拿到 .so 的路径
2. open(path) → 拿到 fd
3. 算出三个段在文件里的偏移（链接脚本或 gen_embed_ohos.py 记录，随符号一起导出）
4. mmap(NULL, 总大小, PROT_NONE, MAP_PRIVATE | MAP_ANON, -1, 0)      ← 先占一整块连续地址
5. 逐块放进去（MAP_FIXED 到预留地址上）：
     代码块：mmap(base+off, len, PROT_READ | PROT_EXEC,
                  MAP_PRIVATE | MAP_FIXED, fd, file_off)              ← 文件映射 → 可执行合法
     W 块  ：mmap(base+off, len, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_FIXED, fd, file_off)              ← 写时复制
```

**与 iOS 一一对应**：

| iOS | 鸿蒙 |
|---|---|
| `getsectiondata` 取段 | `__start_/__stop_` 链接器符号 |
| `vm_allocate` 保留连续地址 | `mmap(PROT_NONE, MAP_ANON)` |
| `vm_remap(copy=FALSE)` 共享签名页 | `mmap(fd, PROT_READ\|PROT_EXEC, MAP_PRIVATE)` |
| `vm_remap(copy=TRUE)` 写时复制 | `mmap(fd, PROT_READ\|PROT_WRITE, MAP_PRIVATE)` |
| 苹果的签名机制保证页可执行 | 鸿蒙的文件映射天然可执行 |

### 3.4 强制接管表（`swforce`）同理

`loader.c` 第 127 行还有一处 `getsectiondata`：

```c
g_force = getsectiondata(&_mh_execute_header, "__DATA", "swforce", &sz);
```

鸿蒙改成：

```c
extern const hle_force_ent __start_dmswforce[], __stop_dmswforce[];
g_nforce = (unsigned)((__stop_dmswforce - __start_dmswforce));
```

生成 `swforce` 表的宏（`hle.h` 的 `HLE_FORCE`）也要从 `__attribute__((section("__DATA,swforce")))`
改成 `__attribute__((section("dmswforce")))`。

## 四、阶段 1 必做的三个真机实验

**这三个实验决定了上面方案成立与否，必须在写代码之前做。**

| 实验 | 内容 | 预期结果 |
|---|---|---|
| **A** | `mmap` 匿名内存 → `mprotect` 成 `PROT_READ\|PROT_EXEC`，看是否成功 | **预期失败**（验证"禁止匿名可执行内存"确实存在） |
| **B** | `mmap` 本应用自己的 `.so` 文件 → `PROT_READ\|PROT_EXEC`，看是否成功 | **预期成功**（这是方案的基石） |
| **C** | 写一个自定义段，看 lld 是否生成 `__start_/__stop_` 符号 | 预期成功（lld 标准行为） |

**如果实验 B 也失败**，那方案要重新设计——退路是把整个映像放进 `.so` 的可执行段，
不搬位置，改用"链接脚本强制布局"让三块在文件里就相邻。**这条退路也要在实验里一并试。**

## 五、顺带发现的其他鸿蒙适配点（本轮新发现）

| 位置 | 问题 | 说明 |
|---|---|---|
| `loader.c` `tsd_check()` | **必须重做** | 它用 `mrs tpidrro_el0` 然后假定 `槽 = tpidrro_el0 + 8*key` —— 这是**苹果 pthread 的 TSD 布局**。musl 的布局不同，而且 Linux 上 `tpidrro_el0` 通常是 0。整个"线程槽"机制要按 musl 的 TLS 重新设计 |
| `loader.c` 第 363 行 | `strlcpy` | BSD 函数；musl 是否提供需确认，没有就自己补一个 |
| `loader.c` 第 6 行 | `TargetConditionals.h` | 第 275 行 `#if TARGET_OS_IPHONE` 要换成鸿蒙自己的条件 |
| `loader.c` 第 234 行 | `CommonCrypto` | 只在 `DM_LOADHASH` 诊断路径用，可以最后再换 |

> **注意 `tsd_check()` 这一条**：它比 Mach-O 那两项更底层——因为**整个"改写器 → 宿主"的桥就是建立在"线程槽 = tpidrro_el0 + 8×键号"这个假设上的**。
> 苹果的 pthread 恰好把 TSD 放在 `tpidrro_el0` 指向的结构里；musl 不是这么放的。
> **这意味着改写器的改写目标要重新设计**（回到适配清单里"改写规则需重做"那一项）。

## 一、为什么先做这一步

原实施计划把 **"鸿蒙 Vulkan 能力不足"** 列为**项目级止损点**：

> 如果阶段 1（能力探测）发现鸿蒙 Vulkan 能力缺口过大 → 停止移植，转向"研究记录"或改用 Android 路线。

图形层是四层里最大的一块（Metal → Vulkan，原计划标为"全项目最大风险点"）。
**先花几分钟问清楚"能不能做"，比埋头写几周图形代码再发现做不了，代价小得多。**

所以这一步的目标不是"学 Vulkan"，而是**拿到一张能力清单，逐条对需求打勾或打叉**。

## 二、需求清单（从上游图形层逐条读出来的）

下表左边是**上游实际用到的能力**（都标了出处），中间是它在 Vulkan 里该落到哪，右边是我的风险判断。

| # | 上游的需求 | 出处 | Vulkan 的落点 | 风险 |
|---|---|---|---|---|
| 1 | **GPU 地址 = CPU 地址**：内存池建成零拷贝缓冲，只支持统一内存设备 | mapping §1「MemoryPool」、README「两层」 | 统一内存（`HOST_VISIBLE + DEVICE_LOCAL`）；或 `VK_EXT_external_memory_host` | ⚠️ **中**，但**有两条路**（见 §3.2） |
| 2 | **贴图格式**：Switch 打包贴图是块线性排布的压缩格式（BCn） | mapping §1「Texture」 | `VkFormat` + 解排布/转码 | 🔴 **最高**（见 §4） |
| 3 | **缓冲地址反查**：任何缓冲地址都要反查成「哪个缓冲 + 偏移」 | mapping 开头两条约定 | `VkBuffer` + 设备地址 | 低 |
| 4 | **TexturesView / Sampler**：边框色只有三种预设 | mapping §1 | `VkImageView`；`VkSampler` 的 `borderColor` 本来就只有三种枚举——**天然对齐** | 无 |
| 5 | **Program**：每个阶段一个函数，按控制段哈希从离线库加载 | mapping §1、README「着色器翻译链」 | `VkShaderModule`（吃 SPIR-V，见 §3.1） | ✅ **无（好消息）** |
| 6 | **参数缓冲（argument buffer）**：按反射 json 把绑定的槽号填进参数缓冲 | mapping §2、§3 | `VkDescriptorSet` / push descriptor | ⚠️ 中（模型不同） |
| 7 | **设备指针**：存储缓冲给着色器的是设备指针（反射里的 `SBUFP` / `UBOP`） | mapping §3 | `bufferDeviceAddress`（Vulkan 1.2） | ⚠️ 中 |
| 8 | **Sync**：记提交的栅栏值，等到 GPU 真完成到该值才放行（`MTLSharedEvent` 的已完成值） | mapping §1「Sync」 | `VkSemaphore`（时间线信号量，Vulkan 1.2） | ⚠️ 中 |
| 9 | **Event**：游戏内存里的 32 位值，写值在 GPU 完成之后发生 | mapping §1「Event」 | 提交后由 CPU 写 / 时间线信号量 | ⚠️ 中 |
| 10 | **命令缓冲**：录进游戏自己的命令内存，提交时回放 | mapping 开头、§2 | 直接录 `VkCommandBuffer` | ⚠️ 中（架构差异，不是能力问题） |
| 11 | **渲染通道**：随时开关渲染编码器；通道第一条命令前的清除并进附件的读入动作 | mapping §2 | 动态渲染（Vulkan 1.3）或传统 render pass | 低 |
| 12 | **TBDR 优化**：附件不读入 / 不写回、通道合并、片元的"可读 tile"版本 | mapping §1「Texture」、README | `loadOp`/`storeOp`、`VK_EXT_load_store_op_none`、动态渲染的 local read | ⚠️ **高**，但**是优化项**：不做也能出画面，只是慢 |
| 13 | **绘制**：四边形图元、8 位索引（上游自己也没实现，遇到报红） | mapping §2 | 同上游（两个三角形拼） | 低 |
| 14 | **计算**：4 个内嵌计算着色器 + 线程组大小取自反射 | mapping §2 | `vkCmdDispatch` | 无 |
| 15 | **计数器 / 计时**：`ReportCounter` 的值在 GPU 完成后写回；逐通道 GPU 时间 | mapping §2、README | 提交后回读 / `timestamp` 查询 | 低 |
| 16 | **出图**：交换链贴图 ↔ 图层；出图裁切；垂直同步 | mapping §1「Window」 | `VkSwapchainKHR` + `VkSurfaceKHR`（对接 `OHNativeWindow`） | 中（**第二阶段**，要窗口） |
| 17 | **脏页跟踪**：用写保护发现游戏内存改了要重传贴图 | mapping §1、`nvn_dirty.c` | 纯平台无关（`mprotect` + 缺页钩子），**已随宿主一起编过** | 无 |

**小结**：17 项里，**11 项风险低或无**，**5 项中等**，**1 项最高（贴图格式）**，
另有 1 项（TBDR 优化）是"不做能跑、做才快"的优化题。

## 三、两个重要的好消息

### 3.1 着色器这一环**不需要新的翻译器**

上游的着色器翻译链是这样的（README）：

```
Switch 原版着色器包（Tegra X1 机器码）
  → tools/dmsh_xlate  … 出 SPIR-V       ← 注意这一步
  → spirv-cross       … SPIR-V → Metal 着色语言
  → xcrun metal       … 编成 metallib
```

**第一步的产物就是 SPIR-V——而 Vulkan 吃的正是 SPIR-V。**

也就是说：**Vulkan 后端可以直接用第一步的产物**，不需要 `spirv-cross`，也不需要新的翻译器。
原计划里写的"着色器翻译链加一个 SPIR-V 后端"，实际上**已经存在了**，只是之前是"顺路经过"。

> **待核实**：`dmsh_xlate` 产出的 SPIR-V 是否是"标准、可直接给 Vulkan 用"的形态
> （比如有没有用上 Metal 特有的扩展指令）。这一条要单独查，**先不当作已解决**。

### 3.2 零拷贝内存**也可能不需要** `VK_EXT_external_memory_host`

上游的做法是"游戏的池内存 → 用 `newBufferWithBytesNoCopy` 包成 Metal 缓冲"，
在 Vulkan 里的直接对应物是 `VK_EXT_external_memory_host`（把主机内存导入成显存）。

**但这里有个更好的做法**：创建内存池这个接口**本来就是宿主实现的**（`hle_nvn.c`）。
既然宿主说了算，它完全可以**用 Vulkan 自己分配内存，再把指针交给游戏**——
这样"GPU 地址 = CPU 地址"天然成立，**根本不需要那个扩展**。

> 这样的好处：少一个设备相关的能力依赖，而且对齐问题（苹果 16 KiB 页那些麻烦）
> 也变成我们可控的——分配时按 Vulkan 的要求对齐就是了。
> **待核实**：游戏对池内存有没有自己的假设（比如要求 CPU 能直接读写、要求特定对齐）。

## 四、最大的单项风险：压缩贴图

- Switch 用的是**桌面式的 BCn 压缩**（BC1/BC3/BC5/BC7…）；
- **移动 GPU 通常只支持 ASTC / ETC2**，不支持 BC。

这件事的影响面很大——游戏里几乎每张贴图都是压缩的。可能的结局：

| 结局 | 应对 | 代价 |
|---|---|---|
| 设备支持 BC | 直接照搬，最省事 | 无 |
| 不支持 BC，但支持 ASTC | 贴图**离线转码** BC → ASTC | 中；上游已有 ASTC 打包路径（`D2RM_ASTC_PACK`）可借 |
| 都不支持 | CPU **解压**成未压缩格式 | 大：显存占用和带宽都会涨 |

好消息是**上游已经准备好了退路**：`DM_TEST_NO_BC=1` 可以在任何机器上强制走"不支持 BC 时的解压路径"，
仓库里也有给老设备用的 ASTC 打包工具。所以这一项是"工作量问题"，不是"能不能做"的问题。

**探针里专门列了 12 种格式逐个查**，就是为了一次把这件事定下来。

## 六、报告怎么判读

报告按"风险从高到低"排好了，重点看三处：

| 看什么 | 怎么判 |
|---|---|
| **贴图格式那一节** | BC 全"无" + ASTC"有" ⇒ 要做转码（可借上游 ASTC 路径）；BC"有" ⇒ 最省事 |

## 九、真机结果（2026-10-14，HUAWEI Mate 70 Pro+ / Maleoon 920）

**结论先行：这条路能走，而且结果比预期好。**

设备画像：**Maleoon 920**（华为自研 GPU，集成）｜ **Vulkan 1.3.309**｜驱动版本 3104880233。
实例创建成功，物理设备 1 个，98 个设备扩展。

### 9.1 五大关键项全齐

| 关键项 | 结果 | 意味着 |
|---|---|---|
| Vulkan 版本 | **1.3** | 1.2/1.3 的核心特性都在，不用一格格拔扩展 |
| 统一内存（`HOST_VISIBLE + DEVICE_LOCAL` 类型） | **有 2 个** | ✅ **零拷贝缓冲可行**——§3.2 那条"宿主自己分配"的路成立 |
| 时间线信号量 `timelineSemaphore` | ✅ | `FenceSync` / `SyncWait` 可直接映射 |
| 缓冲设备地址 `bufferDeviceAddress` | ✅ | 反射里的 `SBUFP` / `UBOP` 可直接映射 |
| 动态渲染 `dynamicRendering` | ✅ | "随时开关渲染编码器"这个模型可以直接对应 |

外加：`VK_KHR_surface` ✅、**`VK_OHOS_surface` ✅**（出图的地基都在）、
`VK_KHR_synchronization2` ✅、`robustness2` ✅（越界读被钳住）、
时间戳 64 位有效 ✅（逐通道 GPU 计时可用）。

**上限也很宽裕**：每阶段存储缓冲槽 500000、颜色附件 8、帧缓冲 16384×16384、
存储缓冲单块 1 GiB、计算工作组 512×512×512。

### 9.2 唯一确定要投入的一项：贴图转码

```
BC1 / BC3 / BC5 / BC7        采样无 渲染无     ← 全不支持
ASTC 4x4 / ASTC 8x8          采样有            ← 支持
ETC2 RGB                     采样有            ← 支持
特性位：压缩贴图 BC 无 / ASTC 有 / ETC2 有
```

Switch 打包贴图用的是 **BC**，这台设备**不支持 BC** ⇒ **贴图必须在手机上转码（BC → ASTC）**。

这一项是"工作量"，不是"能不能做"：上游已经准备好了退路
（`DM_TEST_NO_BC=1` 可在任何机器上强制走解压路径；仓库里也有给老设备用的 ASTC 打包路径）。

### 9.3 三处"扩展没有，但核心能替"

| 缺的扩展 | 影响 | 替代 |
|---|---|---|
| `VK_EXT_load_store_op_none` | "附件不读入 / 不写回" | 用**核心**的 `VK_ATTACHMENT_LOAD_OP_DONT_CARE` / `STORE_OP_DONT_CARE`——TBDR 省带宽的目的能达到（`NONE` 与 `DONT_CARE` 的差别只在"是否保证保留旧内容"这种边角语义上） |
| `VK_KHR_dynamic_rendering_local_read` | "可读 tile"（片元读自己正在写的目标） | 用**传统渲染通道 + input attachment**——这是 Vulkan 1.0 就有的能力，只是渲染通道要用老写法（不能全用动态渲染） |
| `VK_EXT_host_image_copy` | 主机侧直接拷贴图 | 用核心的 `vkCmdCopyImage`，多一次中转，不影响可行性 |

**含义**：这三项都不构成阻塞，但**会改变图形层的写法**——所以要在设计阶段就按"核心能力"来设计，
而不是先照抄 Metal 的写法再回来打补丁。

### 9.4 两个必须跟进核实的点（先不当作已解决）

1. **`vertexPipelineStoresAndAtomics: 无`**——顶点阶段不能用存储缓冲与原子操作。
   要查上游图形层/翻译出的着色器有没有依赖它。**如果有依赖，这是本设备上第一条真限制**，
   需要改着色器（把顶点阶段的计算挪到计算着色器）。
2. **池内存到底是谁分配的**——设备**没有** `VK_EXT_external_memory_host`，
   所以"把游戏 malloc 的内存导入成显存"这条路走不通。§3.2 的方案（宿主用 Vulkan 分配、
   把指针交给游戏）成立的前提是：**NVN 的内存池接口允许宿主决定内存从哪来**。
   要回去核对 `nvnMemoryPoolBuilderSetStorage` 这一族的用法——**如果游戏是自己 malloc 后交给 NVN 的**，
   就要另想绕法。这是本设备上第二条潜在限制。

### 9.5 结论

按第八节的判读顺序逐条过：

1. 能不能建实例、有没有物理设备 → **能，有** ✅
2. 压缩贴图能不能用 → **BC 不行，ASTC 行** ⇒ 要转码（有现成退路）⚠️
3. 统一内存 / 时间线信号量 / 缓冲设备地址 → **全有** ✅
4. 各项上限 → **很宽裕** ✅

**止损点这一关过了。** 图形层可以继续做，且做法已经清楚：
按核心能力设计（DONT_CARE + input attachment + vkCmdCopyImage），把工作量的重心放在**贴图转码**上。
